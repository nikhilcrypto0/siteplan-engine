# siteplan-engine: Agent Instructions

> Last verified: 2026-09-29

An offline "survey to site plan" assistant for a Hyderabad architecture firm (agency client). It reads a surveyor's drawing, checks a proposal against Telangana building rules, prints the firm's area statement, and writes DXF using BuildNow plugin layer names. It is client-facing software: tests, lint and review apply.

## Commands

- Install: `uv sync`
- Tests: `uv run pytest -q` (client-drawing tests skip when `fixtures/` is empty)
- Lint: `uv run ruff check src tests`
- Start a project: `uv run siteplan new` (asks the questions, writes `<name>.project.json`; the only entry point a customer should need)
- Read a survey: `uv run siteplan survey <survey.pdf|survey.dxf> --out out/`
- Rule check: `uv run siteplan check examples/example.project.json` (exit 1 if any rule FAILs)
- Area statement: `uv run siteplan area-statement examples/example.project.json`
- Layout options (Stage 2a): `uv run siteplan layout examples/example.project.json --library examples/flat_library.example.json` (add `--survey <file>` when the project has no `net_plot_m`)

- Assistant (Stage 2b): `uv run siteplan assist examples/example.project.json --library examples/flat_library.example.json --config examples/assistant.config.json --brief "Stilt + 8 floors, 70% 2BHK, rest 3BHK"` (needs a local OpenAI-compatible model: Ollama `qwen3.5:9b` on the Mac, vLLM + Qwen3.6-27B on the office server)
- Rule question: `uv run siteplan rules "is a ramp allowed in the setback"` (searches the order, prints the passage and page) or `uv run siteplan rules --height 35` (the Table IV row, no search). The document lives in gitignored `fixtures/rules/`.
- Rules against real schemes: `uv run siteplan cases` (runs the checker over every `fixtures/cases/*.case.json`, a sanctioned plan or the firm's own drawing; exit 1 while any FAIL is not yet understood)
- Rule inventory: `uv run siteplan inventory` (every rule the engine applies or leaves out, how each was read, and what would settle it; `--markdown` prints a table to share with the firm)
- MCP server for an agent harness: `uv run siteplan-mcp --workspace examples --out out/mcp --approval page --rules fixtures/rules/go168-2012.pdf` (stdio). Tools: `list_files`, `read_survey_drawing`, `check_rules`, `area_statement`, `rules_for_height`, `search_rules`, `propose_layouts`. The Hermes Agent profile that runs it lives outside the repo: `hermes -p siteplan chat` (config in `~/.hermes/profiles/siteplan/config.yaml`).

## Rules

- **Client data never enters git.** Drawings and anything derived from them live in `fixtures/` and `out/`, both gitignored. Examples and tests use made-up geometry.
- **The language model never produces a number.** Areas, scales, setbacks and rule verdicts come from this code. A later LLM layer may fill a `Project` file from a brief and explain findings; it does not compute.
- **The rule set now spans four orders**, each read from its own text: G.O.168 of 2012 (base), G.O.Ms.No.7 of 2016 (green strip only where the setback is 9 m+; parking floors above ground left out of the height for Table IV; rule 16 rewritten so a high-rise that surrenders land for road widening may take setback concessions down to 7 m clear on all sides; amenities rewritten as "upto 3% of the total built up area (or) 50,000 Sft. whichever is lower"; the EWS land rule replaced by a shelter fee), G.O.Ms.No.50 of 2019 (Table IV substituted, plus the note adding setback to buildings over 40 m long, where the length is the long side of the smallest rectangle round the outline: a block turned to suit the site is no longer for it, and a long side with a jog in it is still one side), G.O.Ms.No.95 of 2026 (a high-rise is 21 m; 18-21 m on 750-2000 m² needs TDR). The 2016 order has a text layer; the 2019 and 2026 orders are scanned: their pages were rendered with pypdfium2 and read, which is how any scanned order has to be checked. G.O.119 is Andhra Pradesh law and does not apply. Still unread: G.O.245/2012, G.O.103/2021 (podium parking), G.O.16/2026, TS-bPASS G.O.201.
- **Every rule value carries its clause** (`src/siteplan/rules.py`). Change a value only with the primary source in hand, and update the test in `tests/test_rules.py`. A value known only from news is never a default; read the order first.
- **Every rule is in the inventory** (`inventory.py`, `siteplan inventory`): the value (read from `rules.py`), the clause, and how it was read, as written, interpreted, assumed or not modelled, with the choice we made and the evidence that would settle it. `tests/test_inventory.py` fails when a clause in `rules.py` has no entry, or an entry claims a module applies a rule the module never uses. On 2026-09-29 it counted 39 rules of which only 6 are applied exactly as written, which is why rules are now proven against the firm's sanctioned plans rather than our reading.
- **Sanctioned plans are the test of the rules** (`cases.py`, `siteplan cases`). A case is a real scheme described from the firm's drawing and, once there is one, its approval letter: net plot, building outlines and heights, roads, the evidence (`sanctioned` or `firm_drawing`) and every assumption. It runs through the same checker our layouts face; a FAIL on a sanctioned plan means our rule is wrong. Each case lists the FAILs already understood and why; `test_cases.py` fails on a new one, and on a listed one that stops failing, which is a rule fixed and must be recorded. Cases are client data, in gitignored `fixtures/cases/`. Outlines traced from a drawing must be concave hulls of the walls: a convex hull put a ring-shaped Dhulapally block 4.35 m from the boundary when its nearest wall is 7.82 m. The first case, the firm's own Dhulapally drawing, keeps 8 m round and between its stilt + 8 blocks and 7 m round the stilt + 6 one, which is Table IV for 21-24 m and up to 21 m with no 40 m addition: as if the stilt is not counted, the opposite of our reading.
- **The model does two jobs only:** read the brief into the `BriefExtraction` schema, and (if `model_commentary` is on) add commentary. Comparisons between options are computed in `compare_options`; a live run showed the 9B model mislabel which option sells the most while quoting only real numbers. Numbers it reads are checked against the brief; commentary that ranks options or quotes an unsourced number is dropped.
- **The architect approves the interpreted request before anything is solved** (LangGraph `interrupt`). There is no flag to skip it, and nothing with side effects runs before the interrupt.
- **Token budgets live in the config** (per step, per run, per day, with a daily ledger in `out/usage/`). Crossing one halts the run. Rejections go to `out/logs/assistant.log`, never back to the user.
- Assistant tests use a scripted model and need no server.
- **In the MCP server, the approval is asked of the person, never the model.** Only an explicit approval draws anything; a rejection, a timeout or a client that cannot ask all stop with nothing written. Hermes one-shot mode (`-z`, which also turns on yolo) declines, verified live.
- **Two approval channels, chosen at startup, never falling back to each other** (`--approval`): `elicit` asks through the chat app (Hermes answers accept with an empty form, which is why `Approval.approve` defaults to true); `page` serves one page per request on 127.0.0.1 behind a one-time token that never goes into the tool's reply, so the model can neither see the link nor click it. Falling back would let a real rejection be retried in a channel that might answer differently. **Hermes 0.21 needs `page`:** its chat screen declines every MCP elicitation without showing it (the approval panel is registered on another thread; upstream PR #94520 is open and no longer applies to their tree).
- **The MCP server reads only its `--workspace` folder** and refuses anything else with one generic message (the reason goes to the log). Point the workspace at made-up examples whenever the model runs on a machine the firm does not control.
- **The MCP SDK stays on 1.x** (`mcp<2`) because Hermes 0.21's client is mcp 1.26; move to 2.x only after checking elicitation against the Hermes version in use.
- In the harness path the model calls are Hermes's, so the per-run limit is `agent.max_turns` in the profile; there is no per-day token cap there yet.
- **Amenities take their land before the towers** (`amenities.py`): the club house is reserved inside the setback envelope and subtracted from it (so it is never counted as open space), the driveway ring runs in the setback band outside the envelope. A club house that does not fit raises rather than being silently dropped. Rules from the primary G.O. text: driveway >= 4.5 m (rule 13(c)(viii)); amenities >= 3% of built-up area from 100 units, in a block of their own (rule 15(a)(x), the group-housing clause, in preference to rule 9(o)'s 5% of site which sits in the row-housing section; that is the 2012 minimum, and how the 2016 rewrite is read is an open question in the inventory); parking per Table V row 4, 30% of built-up inside GHMC and 20% elsewhere, counting the stilt and the surface bays, with a shortfall reported NEEDS_INPUT because cellars and podiums are not modelled. The amenities block is sized from the built-up area the search itself decides, so `solve` re-sizes and re-searches (`AMENITY_PASSES`) until the layouts satisfy the rule that sized them, and it is placed by what it costs in flats rather than by hugging an edge.
- **Surface parking goes inside the setback envelope, never in the setback band** (rule 13(b)(iii): parking belongs in the open space over and above the setbacks, where only the drive runs). Bays are 2.5 x 5 m in rows with a 6 m aisle, on what the towers, tot-lot and amenities leave. The entry and exit gates sit on the longest boundary, which is assumed to be the road frontage until something tells us otherwise; the caveat says so.
- **Every option is also drawn up as a sheet** (`sheet.py`, `option_N.sheet.dxf`): an A1 sheet at the tightest standard scale that fits, with dimensions, labels, a north arrow, a scale bar, the area statement and our own title block, all on SHEET-* layers so the firm can switch ours off and keep the BuildNow geometry underneath.
- **A rule question is answered from the order, never from the model's memory** (`rulebook.py`, tools `rules_for_height` and `search_rules`). Heights come from the encoded Table IV; everything else comes back as the passage, its page, and a citation built from the section heading and clause marker in the document. A live run showed why the citation matters: the model quoted page 19 correctly and then called it "rule 7(a)(vii)" when it is rule 13(vii). Ranking is BM25 over clause-sized chunks plus a bonus for words the order splits ("drive way" for "driveway"). With no `--rules` document the search refuses rather than letting the model improvise. **Only the 2012 order is indexed** (the 2019 and 2026 orders are scans; the 2016 order has text but is not indexed yet), so its replaced passages announce themselves: `SUPERSEDED` in `rulebook.py` matches the 2012 wording of Table IV, the 18 m high-rise definition, the green-strip clause, the amenities minimum, the road-widening concessions and the EWS land rule, and every hit carries `superseded_by` and `still_in_force` while `search_rules` adds a `warning`. Without it a live search answered a 27 m setback question with the 2012 table's 9 m, correctly cited to page 13, when the figure in force is 10.6 m.
- **A missing input is reported, not guessed.** Checks return `NEEDS_INPUT` rather than assuming.
- **No AGPL dependencies.** PyMuPDF is AGPL, so PDFs are read with pdfplumber (MIT). Check the licence of anything new before adding it.
- **Every layout option is re-checked by the rule checker** before it is shown, and carries the flat library's note plus the v0 caveat (the club house, drive, bays and gates are drawn; cellar and podium parking, ramps and landscaping are not). The example flat library is illustrative, not the firm's; `fixtures/workspace/flat_library.calibrated.json` is sized against the firm's own Dhulapally area statement and is still assumed, not their blocks.
- **Towers are laid out on the net plot, never the gross** (`load_plot`). When a project states a net area smaller than the surveyed boundary, the difference is land lost to road widening, so `less_road_strip` takes it off the frontage (the longest run, the same boundary the gates assume) rather than evenly all round: an even inset would leave towers standing in the strip the road will take. The basis line says so and asks for `net_plot_m`. Found on the firm's own Dhulapally numbers, gross 20,131 m² against net 18,969 m², where planning on the gross had been inventing 16 flats.
- **A firm's flats are read from its own floor-plan DXF, one flat per kitchen** (`flat_import.py`). Three routes were tried on the firm's Suchitra file and two failed: walls are separate lines broken at every door, so 90 segments polygonized into no flat-sized face; and "MAIN DOOR" is this firm's block for every door, 633 of them against about 78 flats. What works is that the architect writes each room's size into its label ("MASTER BEDROOM 4315X3465") and that a flat has exactly one kitchen, so kitchens count the flats and every other room joins the kitchen it sits nearest. Saleable area is measured (carpet plus the stated common-area loading); the frontage is derived from that area at the shared depth with a 12% wall allowance, because label positions measure the draughtsman's hand, not the flat. A type must repeat, and a grouping with less than 22 m² of carpet per bedroom has swallowed a neighbour's room and is dropped. The depth it measured, 25.79 m, lands within 7% of the 24.13 m calibrated independently from the Dhulapally area statement.
- **The sold area is the plate** (`LayoutOption.saleable_sqft`). A flat sells on its super built-up area, its own walls plus its share of the corridor, the lift core and the staircase, so every square foot of a residential plate is loaded onto some flat. Summing the flats' own footprints instead reported 364,192 sft of sales on a 455,518 sft building, less floor sold than drawn, and the whole suite passed because nothing pinned the relationship; `test_every_square_foot_of_a_plate_is_sold` now does. The loading follows from the drawing rather than a constant (20.5% on Dhulapally, against the 22% the firm's own statement uses and the 29.5% ASBL Spire publishes for a G+35 tower) and is reported as `loading_pct`. The amenities block is built but never sold, which is why built-up stays above saleable.
- **Three areas, and they are not interchangeable.** Carpet is the clear internal size room labels give; built-up adds walls and balconies and is what a firm's area statement prints; saleable adds the common-area loading and is what a flat sells for. Every option reports `built_up_sqft` beside `saleable_sqft` so a scheme can be held against a firm's own statement, and `flat_import` runs carpet through `BUILT_UP_FROM_CARPET` before the loading. Quoting carpet as saleable is how the engine came to show 325,152 sft against the firm's 474,912 on the same site and look a third worse than it was; compared properly it reaches 455,518 sft, within 4% of what their architect drew.
- **The printed scale on a survey sheet is not trusted.** Scale comes from the dimension labels, then snaps to a standard plot scale only when within 0.5% (Dhulapally's was plotted to fit the paper at 1:744.9; all seven labels agree to 0.01%). Every closed shape of every colour is tried as the plot except the sheet frame: keeping the largest shape per colour once returned Suchitra's black frame, 7,239 m², for its black plot of 8,063.8 m². Levels are the sheet's own densest run of decimals, because one survey levels from sea level (583 m) and another from a benchmark of 100.000. A sheet with no dimension labels (Suchitra) is scaled from its written area, the plot being the tightest shape round the spot levels, with a warning that the area is then not an independent check. Areas are read in acres and guntas (with trailing square yards), square metres and square yards, never square feet, and the site area is the largest written.
- The BuildNow layer names in `dxf_export.py` are from the plugin's layer index; whether the plugin accepts pre-named layers is untested (needs Windows, ZWCAD 2025 and the plugin).
- Lines stay at 100 characters or fewer (ruff).
